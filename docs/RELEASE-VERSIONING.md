# CreditSoft prospective release versioning

Developer: Matthew X Murphy, https://MatthewxMurphy.com. Product/support: https://builtnotbegged.com. Existing project license remains MIT. CreditSoft release ownership and distribution remain unchanged.

Future office release identities use YYYY.M.DD.XXX in America/Chicago: unpadded month, two-digit day and counter001–999. Same-day updates increment the counter; the next Chicago day starts001. Dates must exist. Historical versions, tags, packages and release notes retain their original identities and timezones. Old YYYY.M.D.N and legacy three-part previous values remain readable inputs; they are not rewritten in history.

The publisher rejects impossible dates, noncanonical future identifiers, counter overflow, backward automatic dates, explicit versions dated outside Chicago today, and non-Chicago release configuration. Set the future release configuration to America/Chicago through the authorized owner process; changing this source default does not update a real environment. Unknown nonempty previous versions fail closed for explicit releases unless an operator intentionally supplies --required for a reviewed correction. The existing --required contract can correct a lower bad stamp; it cannot reuse the current previous identity. This flag does not authorize publication, replace an immutable package, or establish artifact provenance.

Office feeds, default release-note prefixes, office package names, embedded office manifest versions and package README versions use the same canonical identity. Build identifiers remain a separate field and default to that identity. Eight existing feed mirror paths and technical updater identifiers remain unchanged.

Chrome uses numeric year.month.day.counter in version, with canonical text in version_name. For illustrative 2099.2.03.007, the numeric value is2099.2.3.7. npm uses year.month.(day*1000+counter) in version, with canonical text in creditsoftReleaseVersion; that illustration becomes2099.2.3007. This is a valid three-part encoding with an ordered, reversible day/counter. These examples reserve no release. Existing released Chrome/npm identities are not relabelled by a source checkpoint; only an authorized future publisher invocation prepares future metadata.

A stable companion ZIP's existence cannot establish a new companion version. The publisher keeps its independent feed version instead of stamping it with the office release. A candidate-named intranet installer is still selected by its existing versioned path; existence is not package-content verification. Actual package bytes, independently released component identities, installation compatibility and public distribution require separate evidence.

Validation should use fixed-clock pure calendar controls plus synthetic publisher mirrors under inert Laravel/Carbon/File/service stubs in a fresh owned fixture directory. Cover the previous implementation baseline, Chicago/UTC/Los Angeles boundaries, leap dates, legacy inputs, overflow/backward/unknown versions, explicit --required corrections, Chrome/npm mappings, zero-write failures/dry run, eight matching feed mirrors and preservation of an existing stable companion version. Never bootstrap the app, read actual.env, invoke the office package builder, or connect to a real node merely to test version formatting. Exact commands and raw receipts belong with each reviewed candidate; no completed test is asserted by this document.

Source checkpoint, tested synthetic contract, actual package, authorized publication and verified running node remain separate states. In particular, these changes do not establish issue6 acceptance across web, queue and scheduler. The pre-existing feed-before-optional-package sequencing is not an atomic publication guarantee. Real release publication still requires immutable artifact and owner/license checks, appropriate release notes, safe rollout and verified runtime.

The browser companion reports version_name when present and falls back to the old numeric version for historical manifests. The intranet client reads its adjacent ../package.json relative to its own module URL: a valid canonical creditsoftReleaseVersion first, then a strictly shaped historical three/four-part version string, then the unchanged historical fallback2026.5.6.4 if metadata is missing, invalid or unreadable. No object is stringified into a version. This read touches only bundled package metadata, not operator configuration or provider data. Pure reader tests extract only these two functions and the five identical browser expressions; they do not start the client/router or execute provider capture code.
